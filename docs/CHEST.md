# Chest storage

The Chest is a passive, one-block inventory with 27 slots and the shared
128-item stack cap. A Hopper directly above pushes into it; a Hopper directly
below pulls from it. Right-click opens the storage screen above the full player
inventory. Interactions use the existing source/destination controls and
identity/revision-checked entity requests.

## Foundation reuse

Chest and Hopper share the exact component-preserving inventory port and slot
interaction policy in `entities/storage/`. Chest now uses the public declarative
[storage lifecycle](HOST-LIFECYCLE.md) and a runtime-sized 27-slot payload in
`entities/container.rs`, with `TickPolicy::Never`. It now uses independent BGCT
storage and the shared registered inventory view/screen. Hopper retains its three-slot payload and flow
decisions; its automation does not test whether a neighbor is a Chest.

The shared transaction path still owns both ends of every transfer. Full
destinations refuse deposits, stale revisions reject whole actions, and
retries cannot duplicate player withdrawals. Placement consumes one item;
breaking atomically removes the entity/block and creates the Chest refund and
remaining stack drops. The private codec retains arbitrary stack components.

Public inventory summaries carry slot item/count pairs and optional registered
status fields. Machine kinds are no longer encoded as a closed list; Chest's
27-slot summary is 165 bytes. Components remain server-private.
Client replica assembly, revision checks, and committed publication are shared.

Chest content uses block/item ID 301, state ID 601, entity ID 6, and schema 2.
The registered-inventory slice used `world-v11`; the current dynamic-entity catalog advances the default save directory to `world-v12`.
The new wooden textures are generated by `assets/textures/blocks/source/chest.py`.
